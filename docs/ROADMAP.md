# YamchaMemo 발전 계획

정한 순서와 그 이유, 그리고 이미 내린 결정을 적어 둔다.
(작업 지시서는 `HANDOFF.md`, 이 문서는 "무엇을 왜 그 순서로"만 다룬다)

## 순서

```
1단계  데일리노트 진입 바꾸기          ✅ 0.4.0
2단계  UI 토대 — 디자인 토큰 → 다크 모드  ✅ 0.4.0
3단계  내보내기                       ✅ 0.4.0
4단계  기능개선                       ✅ 0.4.0 (넷 다)
5단계  검색 강화 — 퍼지 + 파일 내부 검색  ✅ 0.5.0
6단계  배포용 hwp + 검색창 다듬기        ✅ 0.5.1
```

## 6단계 — 배포용 hwp와 검색창 다듬기

5단계를 실제로 써 보고 나온 것들만 했다.

- **배포용 hwp**(한글 "배포용 문서로 저장")를 읽는다. 공공기관 공고문에 흔한 형태인데
  5단계에서는 "암호 걸림"으로만 표시했다. 실파일로 검증 완료.
- **토글을 스위치로.** 실앱에서 눌러 보니 분류 칩과 구분이 안 돼 켜고 끄는 것인지
  알 수 없었다. 손잡이가 움직이는 스위치로 바꾸고 `파일 속`을 `첨부내용검색`으로 고쳤다.
- **검색제외 줄.** 검색어와 반대 방향의 조건이라 자기 줄을 준다.

**결정 — 외부 폴더 색인은 이 프로그램의 범위를 넘는다.** 다운로드 폴더 하나가
105개·481MB였고 첫 색인 37.9초였다. 수천 개짜리 업무 폴더는 인덱스도 색인 시간도
자릿수가 달라지고, 거기서부터는 아키텍처가 다른 Docufinder의 영역이다.

**5단계에서 배운 것 — 성능은 재고 나서 판단한다.** "첨부를 색인하면 검색이 느려질 것"이라는
짐작은 틀렸다. 느린 것은 색인 크기가 아니라 발췌 생성이었고,
scope를 후필터에서 색인 쿼리로 옮기고 발췌를 무복사로 고치니 62ms → 8.8ms가 됐다.

4단계를 하며 알게 된 것: 로드맵의 진단 중 셋이 틀렸다. 검색 필터(분류·기간)와
템플릿 변수는 이미 있었고, 화면에 없던 것은 태그 필터 하나와 변수 몇 개뿐이었다.
"재료는 있는데 화면이 없다"고 적을 때는 화면도 열어 봐야 한다.

**3단계를 2단계 뒤에 두는 것이 이 순서의 핵심이다.** "화면에 보이는 모양으로
내보내기"는 결국 화면 스타일을 내보내기용으로 다시 짜는 일이라, 토큰이 정리되기
전에 만들면 토큰을 정리할 때 내보내기도 다시 손봐야 한다.

2단계 안에서도 **토큰 → 다크 모드** 순서를 지킨다. 반대로 하면 다크 모드를 두 번
칠하게 된다.

## 1단계 — 데일리노트 진입

일지는 "오늘 것을 쓰는 곳"이 기본이고, 지난 날짜는 찾아가는 것이다.
지금은 반대로 목록이 먼저 나온다.

- `[📅 데일리노트]`를 누르면 곧장 오늘 노트. 없으면 만든다.
- 노트 헤더에 날짜 이동기: `◀  2026-07-30  ▶   [달력]   [오늘로]`
- 날짜 목록은 없애지 않고 **[지난 일지]**로 남긴다 (3단 보기에서 왼쪽을 채운다).

**결정 — `◀ ▶`는 있는 노트만 오간다.** 안 쓴 날은 건너뛴다. 화살표를 누르다
빈 일지가 줄줄이 생기는 것을 막는다. 달력에서 고른 날짜는 없으면 만든다.

## 2단계 — UI 토대

코드에서 확인한 것만 고친다.

| 문제 | 확인된 근거 |
| --- | --- |
| 타이포 스케일 없음 | 임의 픽셀값 `text-[11px]` 62곳 · `text-[10px]` 26곳 |
| 다크 모드 없음 | `dark:` 0곳 |
| 아이콘 체계 혼재 | 이모지(📚 🔗 🕘)와 글리프(↺ ❝ •)가 한 툴바에 공존 |
| 본문 폭 제한 없음 | `max-w-prose` 계열 0곳 — 넓은 창에서 줄이 너무 길다 |
| 포커스가 사라지는 곳 | `focus:outline-none` 42곳, 대체 표시가 없는 곳이 남아 있다 |
| 색 체계가 둘 | 링크·태그의 보라 vs 콜아웃 팔레트가 따로 논다 |

**결정 — 다크 모드를 만든다.** 설정에서 **라이트 / 다크 / 시스템 설정**을 고르고,
기본값은 **라이트**.

## 3단계 — 내보내기

md 파일 자체는 이미 내보내기가 필요 없다. 필요한 것은 두 가지 성격이다.

- **데이터로** — 책 목록을 CSV(엑셀)와 마크다운 표로. 지금 화면의 필터·정렬을
  그대로 반영하고, 내보낼 항목을 고를 수 있게.
- **보기 좋게** — 독서기록 한 권 · 일지 하루/한 달 · 글쓰기 한 편이나 시리즈를
  스타일이 담긴 HTML로.

**결정 — PDF는 인쇄 대화상자를 거친다.** 앱 안에 PDF 렌더러를 넣으면 용량과
유지비가 크게 오른다. 인쇄용 CSS를 잘 쓰고 WebView2의 "PDF로 저장"에 맡긴다.

## 5단계 — 검색 강화

옵시디언의 옴니서치·텍스트추출기가 하는 일에 **한국 문서(hwp)**를 더한다.
오타·초성을 견디는 검색과, 첨부한 pdf·hwp·오피스 문서의 본문 검색.
자세한 설계·실측은 `HANDOFF-search.md`.

**결정 — Docufinder 코드는 가져오지 않는다.** BSL 1.1이라 프로덕션 사용이 금지돼 있고
(2030-04-15에 Apache 2.0 전환), 포팅하면 그 제약이 이 프로젝트에 따라 붙는다.
어차피 파싱 본체는 상위 OSS 크레이트들이라 그것을 직접 쓴다.

**결정 — OCR은 넣지 않는다.** 텍스트 레이어가 있는 문서만 읽는다. Docufinder는 같은 기능에
PaddleOCR+ONNX 모델 420MB를 쓴다. 우리 추가 용량은 약 3MB다. 대신 "스캔본이라 안 잡힌다"를
화면에서 알려 준다 — 실측 코퍼스에서 PDF의 22%가 스캔본이었다.

**결정 — hwp 파서를 직접 쓴다.** `hwpers` 크레이트가 실파일에서 파싱을 실패했다.
OLE 컨테이너 + raw deflate + `PARA_TEXT` 레코드 스캔은 120줄이고 새 의존성이 없으며,
**표 안의 셀 텍스트까지 잡힌다** — 공고문·양식 같은 한국 문서에서 이게 결정적이다.

**결정 — 기능은 검색창 토글로만 켠다.** 설정에 묻어 두지 않는다.
`≈ 오타 허용`과 `📄 파일 속` 둘 다 기본 꺼짐이고, 끄면 지금까지와 동작이 같다.

**결정 — 첨부는 노트와 같은 색인 필드에 넣는다.** 스키마를 늘리지 않으려는 것이고,
덕분에 끌 때 `type = "_file"` term 하나로 일괄 삭제돼 **인덱스가 원래 크기로 돌아온다**.
제목 자리에 파일 이름이 들어가므로 파일명 검색이 공짜로 딸려 온다.

**5단계를 하며 알게 된 것**: 느린 원인은 색인 크기가 아니라 발췌 생성이었다. 첨부 155건을
넣어도 노트 검색 속도는 그대로였고(3.2 → 3.5ms), 첨부 검색만 15~20배 느렸다.
scope를 후필터에서 색인 쿼리로 옮기고 발췌를 무복사로 고치니 62ms → 8.8ms가 됐다.
"성능이 걱정되면 먼저 재라" — 짐작한 원인은 틀렸다.

## 4단계 — 기능개선

재료는 있는데 화면이 없는 것부터. 넷 다 하기로 했고, 위에서부터 값이 크다.

1. **검색 필터 UI** — 백엔드에 `search_filtered`(분류·태그·기간)가 이미 있는데
   화면은 단순 검색만 쓴다. 가장 싸게 체감이 크다.
2. **주간/월간 회고** — 여러 날의 기록·할 일을 모아 보는 화면. 매일 쓰는 흐름과 맞는다.
3. **태그 관리** — 이름 바꾸기·병합. 태그가 늘면 반드시 필요해진다.
4. **템플릿 강화** — 분류별 새 노트 서식에 날짜 같은 변수.

## 자동 태그 (번호 없는 별도 기능)

1~6단계, 그리고 지금 진행 중인 7단계(`HANDOFF-capture.md`)와 독립적으로 진행한
기능이라 번호를 붙이지 않는다. 태그 관리(4단계-3)는 있는 태그를 다루는 것이고,
이건 "이 노트에 무슨 태그를 달지"를 골라 주는 것이다.

**결정 — 제안만 한다, 파일을 조용히 고치지 않는다.** [audit.rs](../crates/yamcha-core/src/audit.rs)의
"자동 수정 없음" 원칙과 같다. 화면에 칩으로 뜨고, 누른 것만 frontmatter에 들어간다.

**결정 — 고유명사만 제안한다. 후보 출처는 vault 사전뿐이다.**
처음에는 빈도·위치로 일반 키워드도 뽑았는데, 실사용 첫날 "실제로"(필러 부사)가
새 태그로 제안됐다. 불용어를 60여 개 늘려 막았지만, 이 방식은 한국어 부사·담화표지가
끝이 없어서 목록을 영원히 늘려야 하는 싸움이다. **일반 키워드 추출을 통째로 껐다.**

대신 vault 자체를 고유명사 사전으로 쓴다 — 사용자가 이미 "이건 이름이다"라고
표시해 둔 것들이다:

| 출처 | 얻는 것 |
| --- | --- |
| 기존 태그 | 이미 태그로 삼기로 정한 이름 |
| 다른 노트의 제목 | 책 제목, 인물·프로젝트 노트명 (데일리는 제목이 날짜라 제외) |
| 책 frontmatter `author` | 인명 |
| 책 frontmatter `publisher` | 기관명 |
| 영문 대문자 낱말 | Rust, Tauri — 한글과 달리 대문자가 분명한 신호다 |

추측하지 않고 **대조**만 하므로 사전에 없는 말은 제안되지 않는다. 표기가 다르면
[korean.rs](../crates/yamcha-core/src/korean.rs)의 `is_near`로 vault 쪽 표기를 제안한다.

**한계 — vault에 없는 처음 보는 이름은 못 잡는다.** 일지에 "어제 김상욱 교수 강연"
이라고 썼는데 그 이름이 vault 어디에도 없으면 사전에 없으니 제안하지 못한다.
이 구멍이 실제로 자주 느껴지면 그때 형태소 분석기(NNP 태그)를 다시 잰다.

**결정 — 범주는 고유명사를 따라온다.** 본문의 "클린 코드"가 `Books/클린 코드.md`이면
그 노트의 `genre`(컴퓨터/IT)를 범주 태그로 함께 제안한다. vault가 이미 해 둔 분류를
물려받는 것이라 별도 지식베이스가 필요 없다. 화면에서는 호박색 칩으로 구분한다 —
본문에 그 말이 없고 분류에서 따라온 것이라 성격이 다르다.

**결정 — `contains()`로 태그를 찾지 않는다.** 태그 "책"이 책상·정책에, "일기"가
일기예보에 걸리는 것을 막아야 한다. 한글은 어절의 표제어(조사를 뗀 것)와 정확히
일치할 때만, 영문·숫자는 정규식 단어 경계로 매칭한다. 1글자 태그는 그 규칙을
통과해도 제목·헤딩 등장만 인정한다(본문 등장은 너무 광범위하다).

**결정 — 띄어쓰기는 무시하고 찾되, 짧은 이름에는 열지 않는다.** 책 제목이
"창조 기사 논쟁"인데 본문에는 "창조기사논쟁"이나 "창조기사 논쟁"으로 적기 마련이라,
그대로면 제안이 안 뜬다. 공백을 지우고 부분 문자열로 찾는다. 부작용을 세 겹으로 막는다:

1. **길이 문턱** — 붙인 길이가 4자 이상(여러 어절 이름은 3자 이상)일 때만. 이게 없으면
   "독서"가 독서실·독서회에, "일기"가 일기예보에 다시 걸린다.
2. **줄을 넘지 않는다** — 본문 전체를 한 덩어리로 붙이면 목록의 `- 창조` 다음 줄
   `- 기사 논쟁`이 이어져 없던 언급이 생긴다. 줄 단위로만 붙인다.
3. **구두점은 지우지 않는다** — 공백만 지우므로 "그건 창조. 기사 논쟁과는"처럼
   문장이 끊긴 자리는 매칭되지 않는다.

**데일리노트도 제안 대상이다** (제외되는 것은 book뿐 — `BookView`가 따로 그린다).
다만 빠른 입력 바(`DailyEntryBar`)의 textarea는 한글 조합 충돌을 막으려고 값을
React state로 올리지 않으므로, **타이핑 중에는 제안이 갱신되지 않고 `[추가]`로
기록이 파일에 들어간 뒤에 뜬다.** IME 안정성이 우선이라 이 순서를 바꾸지 않는다.

**결정 — 문서 희소도(idf)는 넣지 않는다.** vault 전체 본문을 훑어야 하는데 값이
불확실하다. 사전 대조 방식으로 바꾼 뒤로는 후보 자체가 좁아서 필요가 더 줄었다.

**결정 — 한글 형태소 분석기(kiwi-rs 등)는 도입하지 않는다.** 검토한 `kiwi-rs`는
순수 Rust가 아니라 C++ Kiwi에 대한 네이티브 바인딩이라 빌드 시 .dll을 내려받고
별도 모델 데이터 파일이 필요하며, 라이선스가 LGPL-2.1(배포 시 별도 고지·재링크
허용 필요)이고 유지보수가 활발하지 않다.

**용량 실측**: Kiwi 모델 데이터가 88MB(압축 기준, kiwipiepy-model), 네이티브
라이브러리가 3~5MB다. 지금 실행파일 21.36MB에 더하면 110MB대가 된다 — 앱이 5배가
된다. 이 프로젝트는 OCR에서 같은 판단을 한 번 했다(PaddleOCR 420MB 모델을 접고
약 3MB 대안을 골랐다, 위 "PDF·OCR" 항목). Kiwi의 88MB는 그보다 작지만 지금까지
기능 하나에 받아들인 용량의 30배다.

대신 조사를 문자열 규칙으로 떼는 가벼운 방식(`autotag.rs`의 `strip_particle`)을
쓴다. 의존성 0이고, 사전 대조 방식에서는 "본문의 어절이 사전의 이름과 같은가"만
판단하면 되므로 이 정도로 충분하다.

**규칙 방식의 한계선(실측)**: 바닥글자 "로"를 조사 목록에 넣으려다 뺐다 —
"도로·경로·제로·진로·회로"가 "도·경·제·진·회"로 뭉개진다. "책을→책"은 원하는데
"정도→정"은 원치 않는 것이 규칙상 **똑같은 모양**이라 문자열만으로는 못 가른다.
2음절 낱말과 1글자 조사의 충돌은 형태소 분석기 없이는 원천적으로 안 풀린다.
이런 사례가 쌓이면 위 용량을 다시 저울에 올린다.

**결정 — LLM(Groq 등)은 이번에 넣지 않는다.** 로컬 규칙 엔진은 "이 말이 본문에
있다"까지만 안다. 문맥으로 새 태그를 추론하는 것은 LLM만 할 수 있지만, 버튼을
눌러야만 나가게 하고(자동 호출 금지 — 무료 한도·프라이버시), vault 태그 어휘를
프롬프트에 넣어 새 말을 지어내지 않게 제약해야 한다는 설계만 정해 두고 유예했다.
