# 5단계 — 검색 강화 (퍼지 + 파일 내부 검색)

목표는 둘이다. **오타·초성에도 걸리는 검색**과 **첨부 문서(pdf·hwp·오피스) 본문 검색**.
제약도 둘이다. **앱이 무거워지지 않아야 하고**, 기능은 **검색창 토글로 끌 수 있어야 한다**.

참고한 것: 옵시디언 [Omnisearch](https://github.com/scambier/obsidian-omnisearch)(퍼지·발췌),
[Text Extractor](https://github.com/scambier/obsidian-text-extractor)(추출 결과 캐시),
[Docufinder](https://github.com/chrisryugj/Docufinder)(한국형 문서 포맷 대응).

---

## 1. 지금의 검색 — 코드로 확인한 사실

`crates/yamcha-core/src/search.rs` (401줄), tantivy 0.24, 인덱스는 `.yamcha/search`.

| 항목 | 현재 구현 |
| --- | --- |
| 색인 대상 | **타입 폴더의 `.md`만** (`vault.list_notes()` → `_` 시작 파일 제외) |
| 필드 | `path`(STRING) · `title`·`body`·`tags`(ngram 1–2 + LowerCaser) · `type`·`date`(STRING) |
| 쿼리 | `QueryParser` + `set_conjunction_by_default()`, 부스트 title 3.0 / tags 2.0 |
| 필터 | 타입·기간·태그 — 색인 쿼리가 아니라 **결과 후필터** (넉넉히 받아 걸러냄) |
| 발췌 | 쿼리 토큰 첫 등장 위치 ±50자, 한글 안전(char 단위) |
| UI | `SearchModal.tsx` — 150ms 디바운스, 50건, 타입 칩·기간 셀렉트·태그 칩, `<mark>` 강조 |
| 갱신 | 저장 시 `refresh_note` → upsert+commit, 외부 변경은 watcher가 잡음 |

**잘 되어 있는 것** — 1–2그램 토크나이저 덕에 한글 부분 문자열이 이미 된다("클린"→"클린 코드").
필터·발췌·강조·새 창 열기까지 UI가 갖춰져 있고, watcher가 인덱스를 항상 최신으로 유지한다.

**없는 것 / 약한 것**

1. **오타 허용 0** — ngram은 부분 문자열이지 편집거리가 아니다. "클닌 코드"는 아무것도 못 찾는다.
2. **초성 검색 0** — "ㅋㄹㅋㄷ"로는 못 찾는다.
3. **첨부 문서 본문 0** — `_attachments/`의 pdf·hwp·docx는 검색에 아예 존재하지 않는다.
   파일명 검색조차 안 된다 (색인 대상이 `.md`뿐).
4. **긴 쿼리 정밀도** — 1–2그램을 AND로 묶으므로 인접성 보장이 없다. "코드리뷰"는
   `코드`·`드리`·`리뷰`가 흩어져 있는 문서에도 걸린다. 지금은 티가 안 나지만
   퍼지를 켜서 후보를 늘리면 바로 드러난다 → 리스코어가 필요한 실질적 이유다.

## 3. 포팅 가능성 — 포맷별 판정

| 포맷 | 방법 | 크레이트 | 라이선스 | 판정 |
| --- | --- | --- | --- | --- |
| PDF (텍스트 레이어) | `extract_text` | `pdf-extract` 0.12 | MIT | ✅ 순수 Rust. malformed에 **실제로 패닉** → 격리 필수(실측 확인) |
| **HWP 5.0 (바이너리)** | **자체 파서** — OLE + raw deflate + `PARA_TEXT` 레코드 | `cfb` + `flate2` (둘 다 **이미 의존성 트리에 있음**) | MIT/Apache | ✅ **실파일 24/24 성공.** `hwpers`는 탈락(아래) |
| HWPX | zip + XML 태그 제거 | `zip` | MIT | ✅ docx와 같은 코드 경로 |
| DOCX / PPTX | zip + XML 태그 제거 | `zip` | MIT | ✅ 6/6 · 1/1 성공 |
| XLSX / XLS | 시트 순회 | `calamine` 0.36 | MIT | ✅ 13/16 성공(나머지 3은 암호 걸린 파일) |
| TXT / CSV | 인코딩 감지 후 읽기 | `encoding_rs` (**이미 있음**) | MIT/Apache | ✅ CP949/EUC-KR 대응 |
| HWP 배포용 문서(ViewText) | AES-128-ECB 복호 + 난독화 역변환 | `aes` | MIT/Apache | ✅ 6단계에서 구현 (§9) |
| HWP 3.0 (1996~2002) | — | (Docufinder `kordoc`뿐) | BSL | ❌ 범위 밖 |
| 스캔 PDF·이미지 | OCR | PaddleOCR/Tesseract | — | ❌ 범위 밖 (모델 수백MB) |

**`hwpers`는 쓰지 않는다.** 실파일에 대고 재 보니 `HwpReader::from_file`이
`IO error: failed to fill whole buffer`로 파싱 자체를 실패했다. **원인은 특정하지 않았다** —
그 파일은 배포용 문서가 아니었으므로(플래그 확인) 배포용 처리 경로 때문은 아니다.
게다가 `zstd`·`xz2`·`image`를 함께 끌고 온다.

대신 **HWP 5.0 평문 추출을 직접 구현했고, 그게 더 잘 된다.** 원리는 단순하다 —
OLE(CFB) 컨테이너에서 `BodyText/Section*` 스트림을 꺼내 raw deflate로 풀고,
레코드 헤더(tag 10비트 · level 10비트 · size 12비트)를 훑어 `HWPTAG_PARA_TEXT`(67)만 골라
UTF-16LE로 디코드한다. 확장 컨트롤 문자(표·그림 등, 8워드 차지)만 건너뛰면 된다.
**표 안의 셀 문단도 같은 스트림의 PARA_TEXT 레코드**라서 함께 잡힌다 — 공고문·양식 같은
표 범벅 한국 문서에서 이게 결정적이다. 약 120줄, 새 의존성 0개.

`PrvText`(미리보기 평문) 폴백은 불필요해졌다. 참고로 지정 샘플에서 PrvText는 1,023자였고
자체 파서는 **208,877자**를 뽑았다.

## 4. 설계 — 무게를 어디서 아끼는가

### 4-1. 퍼지 검색 — 구현하며 바뀐 것 (실측)

계획은 "스키마 변경 0, 재색인 0"이었다. **절반만 지켰다.** 제목 파생 필드 둘을 추가했다.

| | 계획 | 구현 |
| --- | --- | --- |
| 오타 회수 | 기존 1·2그램에 min-should-match | 음절 **1그램만** + 오타 예산 (2그램은 오타에 해롭다) |
| 오타 검증 | 자모 편집거리 리스코어 | 같음 (`is_near` = 오타 예산 방식) |
| 초성 검색 | 제목 캐시 선형 훑기 | **`title_cho` 색인 필드** (캐시보다 단순·정확) |
| 제목 오타 강화 | (없음) | **`title_jamo` 색인 필드** 추가 |
| 스키마 변경 | 없음 | 있음 → 업그레이드 시 1회 재색인 (노트 2,000건 **0.9초**) |

**왜 비율 문턱을 버렸는가** — 처음엔 "n그램 중 60%가 맞으면 후보"로 했는데 3음절 쿼리의 오타를
못 잡았다. 오타 하나가 망치는 그램 수가 그램 크기마다 다르기 때문이다. "소나키"는 1·2그램 5개 중
2개만 남아(아·라) 60%를 못 넘는다. 그래서 문턱을 **오타 예산에서 산술로 유도**한다 —
음절 1그램은 오타당 1개, 자모 2~3그램은 오타당 5개(2그램 2 + 3그램 3)를 잃으니
`need = 그램수 − 손실×예산`. 예산은 자모 6개당 1개다(`korean::error_budget`).

**왜 제목 필드를 늘렸는가** — 본문까지 자모로 색인하면 인덱스가 몇 배가 되지만, **제목은 짧아서
거의 공짜다**(2,000건 인덱스 2.8MB, 계획 단계의 3.1MB와 차이 없음). 캐시를 손으로 관리하는 것보다
색인 필드가 단순하고, `open()`이 스키마 변경을 감지해 재색인하는 길이 이미 있었다.

**퍼지 비용 실측** (노트 2,000건, 20회 평균)

| 쿼리 | 퍼지 OFF | 퍼지 ON |
| --- | --- | --- |
| "독서" (정확히 맞는 말) | 1.35ms | **1.46ms** — 정확 결과가 다 차면 완화 쿼리를 건너뛴다 |
| "토크나이져" (오타) | 0건 | **10.3ms**, 50건 |
| "ㅌㅋㄴㅇㅈ" (초성) | 0건 | **1.0ms**, 50건 |
| "코두 리뷰" (맞는 게 없음) | 0건 | 0.5ms, 0건 |

목표 150ms의 1/15이다. **정확 검색으로 결과가 채워지면 퍼지는 아무 일도 하지 않는다** —
평소 타이핑에는 비용이 없고, 오타를 냈을 때만 값을 치른다.

**남는 한계** — 본문 오타 검증은 앞 5,000자까지만 본다(`FUZZY_BODY_SCAN`). 자모 편집거리가
O(쿼리×대상)이라 20만 자 첨부 본문을 후보마다 훑으면 타이핑 중에 체감된다. 짧은 쿼리(2~3음절)의
본문 오타는 vault가 커지면 후보 상한(100건)에 밀려 놓칠 수 있다. 제목·태그 오타는 영향 없다.

### 4-1b. 원래 계획과 달라진 점 (기록)

처음 계획은 "스키마를 건드리지 않고 쿼리만 고친다"였다. 인덱스에 이미 1그램이 있으니
완화 쿼리(min-should-match)로 오타를 회수하고, 초성은 `SearchEngine`이 들고 있는 제목 캐시를
선형으로 훑자는 것이었다.

구현하며 둘을 바꿨다.
- **초성은 제목 캐시가 아니라 색인 필드**(`title_cho`)로. 캐시를 upsert/remove/clear마다
  손으로 맞춰 주는 것보다 색인 필드가 단순하고, 제목은 짧아 비용이 거의 없다.
- **완화 쿼리의 문턱은 비율이 아니라 오타 예산**으로. 비율(60%)은 짧은 쿼리에서 오타 하나를
  못 넘겼다(§4-1).

그 대가로 스키마가 바뀌어 업그레이드 시 재색인이 한 번 필요해졌다 — 노트 2,000건 0.9초.

### 4-2. 첨부 문서 검색 — 스키마 변경 0, 끄면 인덱스가 줄어든다

**결정 — 첨부를 기존 tantivy 인덱스에 같은 필드로 넣는다.** 새 필드를 만들면 스키마가 바뀌어
`open()`이 인덱스를 지우고 전체 재색인한다. 필드를 재활용하면 그럴 일이 없다.

```
path  = _attachments/2026-07/보고서.pdf
title = 보고서.pdf          ← 파일명 검색도 이걸로 공짜로 된다
body  = 추출한 텍스트
type  = "_file"             ← 이 한 값으로 필터·일괄삭제가 다 된다
date  = 파일 수정일
```

- **끄기**: `delete_term(type, "_file")` + commit → 인덱스가 원래 크기로 되돌아간다. 즉시.
- **다시 켜기**: 추출 텍스트는 SQLite에 남아 있으므로 **재추출 없이** 색인만 다시 채운다 (Text Extractor의 캐시 아이디어).
- **후필터**: `SearchFilter.include_files == false`면 `type == "_file"` 결과를 버린다. 타입 칩에는 노출하지 않는다.

추출 캐시는 기존 `.yamcha/index.db`에 테이블 하나:

```sql
CREATE TABLE IF NOT EXISTS doc_text(
  path TEXT PRIMARY KEY, mtime INTEGER NOT NULL, size INTEGER NOT NULL,
  ext TEXT NOT NULL, chars INTEGER NOT NULL, text TEXT NOT NULL,
  status TEXT NOT NULL   -- ok | empty | encrypted | failed | too_big | unsupported
);
```

`mtime`·`size`가 같으면 건너뛴다. `failed`·`encrypted`도 **기억한다** — 깨진 파일이나 암호 문서를
켤 때마다 다시 붙들지 않기 위해서다(설정에서 초기화 가능). `empty`는 스캔본 신호로 쓴다(§4-3).

추출 안전장치(전부 실측 근거가 있다, §3-1):
`catch_unwind`로 pdf-extract 패닉 격리 · **PDF 50MB / 컨테이너 300MB** · 200,000자 상한 ·
파일 하나마다 취소 플래그 확인 · 백그라운드 스레드 1개(코어를 다 쓰지 않는다).

### 4-2b. 진행형 검색 — 노트 먼저, 첨부는 뒤에 붙인다 (실측 근거)

"첨부를 색인하면 검색이 느려지지 않나"를 벤치로 재 봤다
(`cargo test -p yamcha-core search_scale_bench -- --ignored --nocapture`,
노트 2,000건 + 첨부 155건(3만 자 150개 + 20만 자 5개), 쿼리당 20회 평균).

| | 개선 전 | 개선 후 |
| --- | --- | --- |
| 노트만 있는 인덱스 · 일반 검색 | 3.8 / 4.9 / 5.8ms | **1.6 / 3.1 / 3.0ms** |
| 노트+첨부 인덱스 · 노트 검색 | 3.2 / 5.3 / 5.3ms | **2.0 / 3.5 / 4.5ms** |
| 첨부 검색 | 62 / 72 / 61ms | **8.8 / 13.5 / 13.3ms** |

**밝혀진 것 — 느린 원인은 색인 크기가 아니라 발췌 생성이었다.** 첨부 155건을 넣어도 노트 검색
속도는 그대로다(3.2 → 3.5ms, 노이즈 수준). 반면 첨부 검색은 15~20배 느렸는데, 원인이 둘이었다.

1. **scope를 후필터로 하면 걸러질 문서의 본문까지 압축 해제한다.** 필터가 활성이면 색인에서 200건을
   받아 오고, `searcher.doc()`이 그 200건의 저장 필드를 전부 푼다 — 본문이 20만 자인 문서가 섞이면
   이게 검색 시간을 지배한다. → **scope를 `type` 필드 term 쿼리로 옮겼다**(Notes는 `MustNot`,
   Files는 `Must`). 이제 50건만 푼다.
2. **`excerpt()`가 본문을 char 벡터로 두 번 복사했다.** 20만 자면 매 히트마다 1.6MB 할당이다.
   → 바이트 단위 대소문자 무시 검색으로 바꿔 **복사를 없앴다**. 노트 검색까지 2배 빨라진 건 이 덕이다.

**그래도 2단으로 나눈다.** 8.8ms는 사람이 못 느끼지만, 첨부가 150개가 아니라 1,500개가 되면
그만큼 늘어난다. 반면 **1단계(노트) 응답은 첨부가 몇 개든 영향받지 않는다** — 첫 페인트 지연을
구조적으로 0으로 묶어 두는 것이 이 분리의 값이다. 게다가 scope가 색인 쿼리인 이상 두 번 묻는 것이
자연스럽다.

```
입력 → 150ms 디바운스 → ① search(scope=Notes)  → 즉시 렌더 (2~4ms)
                        ② 토글 ON이면 search(scope=Files) → 아래에 append (9~13ms)
```

두 응답 모두 요청 일련번호로 검사해 늦게 온 옛 응답은 버린다(입력이 계속되면 순서가 뒤집힌다).

### 4-3. UI — 설정이 아니라 검색창 토글

`SearchModal`의 기간 셀렉트 옆에 칩 두 개. 상태는 `settings.json`에 저장(`searchFuzzy`, `searchInFiles`,
기존 `theme`·`todoBig`과 같은 `useVault` 패턴).

```
┌──────────────────────────────────────────────────────────┐
│ 검색 (제목·본문·태그)                                     │
├──────────────────────────────────────────────────────────┤
│ [일지][책][글]        ≈ 오타 허용  📄 파일 속   전체 기간 ▼│
│                                    └ 문서 12/48 읽는 중… │
├──────────────────────────────────────────────────────────┤
│ 일지  독서 기록 …                              2026-07-30 │
│ PDF   2026 사업계획.pdf  …해당 대목 발췌…       2026-06-11 │
└──────────────────────────────────────────────────────────┘
```

- `📄` 첫 ON → 백그라운드 추출 시작, 칩 아래 진행률(`file-index-progress` 이벤트). 검색은 그 동안도 된다.
- 파일 결과 행: 확장자 배지 + 폴더 경로, 클릭 → `opener`로 기본 앱, Ctrl+클릭 → 폴더에서 보기.
- **안 잡히는 문서 안내**: 결과 아래에 "텍스트가 없는 문서 12개(스캔본) · 암호 걸린 문서 10개".
  실측 코퍼스에서 PDF의 37%가 여기 해당했다 — 이 안내가 없으면 "검색이 안 된다"로 오해한다.

### 4-4. 무게 예산 (검증에서 실측해 이 표를 채운다)

| 항목 | 목표 | 실측 |
| --- | --- | --- |
| 실행파일 증가 | ≤ +8MB (다운로드·모델 0) | **+2.04MB** ✅ (23.40 → 21.36MB) |
| 첨부 105개 최초 추출+색인 | ≤ 60초, UI 멈춤 없음 | **37.9초** ✅ |

### 5-2. 문서 추출기 — ✅ 완료

- 새 파일 `crates/yamcha-core/src/extract.rs` — 프로토타입 이식 + `Encrypted` 상태 분리

- **Cargo feature `docs`** (기본 on) — 끄면 추출기 전체가 빠지고 `extract()`가 늘 `Unsupported`를
  돌려준다. 두 조합 모두 테스트 통과(ON 137개 / OFF 132개)
- 새 크레이트는 `zip`·`calamine`·`pdf-extract` 셋뿐. `cfb`(0.7)·`flate2`·`encoding_rs`는
  이미 트리에 있던 버전에 맞춰 중복을 피했다
- **fixture를 저장소에 넣지 않았다.** zip 기반 포맷(docx·pptx·hwpx)은 테스트가 그때그때 zip을
  만들어 쓴다. 개인 문서를 커밋할 일이 없고, 파서 경로는 그대로 통과한다
- 바이너리 hwp는 fixture로 만들 수 없어(OLE 컨테이너) 실파일 검증 테스트를 남겼다:
  `YAMCHA_DOC_SAMPLE=<경로> cargo test -p yamcha-core real_document -- --ignored --nocapture`
  → 기준 파일(공고문 hwp)에서 20만 자·27ms·깨진 문자 0 확인
- 커밋: `5단계-2 — pdf·hwp·오피스 텍스트 추출`

**실행파일 크기 실측** (릴리스 빌드 2회, 2026-07-31)

| | 크기 | 추출기 흔적 |
| --- | --- | --- |
| `docs` 켬 (배포 기본값) | 24,551,936 B (23.41 MB) | 있음 |
| `docs` 끔 (`default-features = false`) | 22,400,512 B (21.36 MB) | 없음 |
| **차이** | **+2,151,424 B (2.05 MB)** | |

목표 +8MB의 4분의 1이다. 스파이크 단계의 추정치(+3.1MB)보다도 작다 — 그때는 파서만 담은
단독 바이너리였고, 실제 앱에서는 `flate2`·`cfb`·`encoding_rs`가 이미 링크돼 있어 겹치는 만큼 덜 든다.

컴파일 중인데 `target/release/yamcha-app.exe`를 읽어 **이전 세션의 낡은 exe**를 쟀다.
크기가 같게 나오면 빌드가 끝났는지부터 의심해야 한다 — 판별법은 바이너리에서
추출기 문자열(`"OLE 컨테이너"`)을 찾아보는 것이다. 없으면 그 빌드에는 추출기가 없다.

### 5-3. 첨부 색인 + 커맨드 — ✅ 완료

- 새 파일 `crates/yamcha-core/src/file_index.rs` — `list_attachments`(표지 폴더 제외) ·
  `build` · `rebuild_from_cache` · `drop_all` · `refresh_one` · `status_of`
- `search.rs` — `remove_by_type()` 추가. 토글을 끌 때 `_file` term 하나로 첨부를 일괄 삭제한다
  (스키마를 늘리지 않은 값이 여기서 나온다)
- `commands.rs` — `file_index_status` · `build_file_index`(백그라운드) · `drop_file_index` ·
  `reset_file_index`. 진행은 `file-index-progress`, 완료는 `file-index-done` 이벤트
- `watcher.rs` — 토글이 켜져 있을 때만 `_attachments/` 변경을 따라간다
- 테스트 5개: 지원 확장자만 목록에 · build로 잡히고 drop으로 사라짐 ·
  **drop 후 캐시는 남아 재추출 없이 복구** · 취소가 즉시 먹음 · 못 읽은 문서가 현황에 보고됨

**설계에서 하나 고쳤다 — 잠금 구간.** 처음엔 `build`이 `&mut Indexer`·`&mut SearchEngine`을
받게 만들었는데, 그러면 커맨드가 추출 내내 `AppState` 잠금을 쥐고 있어야 한다. PDF 한 건이
15초 걸리는 동안 **다른 모든 커맨드가 멈춘다** — 백그라운드로 돌린 의미가 없어진다.
그래서 `IndexAccess` 트레이트를 두어 **잠금 구간을 호출자가 정하게** 했다.
추출은 잠금 밖, 색인 쓰기만 잠금 안이다.

8. 앱 재시작 → 두 토글 상태가 유지되는가
9. 깨진 pdf·암호 걸린 문서를 넣어도 앱이 죽지 않는가 (패닉 격리)
10. 스캔 PDF만 넣었을 때 "텍스트가 없는 문서" 안내가 뜨는가
11. `pnpm release:win` → NSIS exe 생성, **전/후 크기 비교**를 표에 기록

## 9. 6단계 — 배포용 hwp 지원 (2026-07-30)

한글의 **"배포용 문서로 저장"** 은 본문을 `BodyText/`가 아니라 `ViewText/`에 넣고 AES-128-ECB로
잠근다. 공공기관 공고문·안내문에 흔한 형태다. 5단계에서는 `encrypted` 상태로 표시만 하고 넘어갔다.

**구조** — `FileHeader`의 속성 플래그 bit 2(`0x04`)가 배포용 표시다.
각 `ViewText/SectionN` 스트림은 앞머리 260바이트(레코드 헤더 4 + 데이터 256)가 열쇠 꾸러미이고,
그 뒤부터가 암호문이다. 열쇠는 이렇게 꺼낸다.

1. 256바이트의 앞 4바이트가 seed (i32 LE)
2. seed로 **MSVC `rand()`와 같은 선형 합동 생성기**를 돌려 XOR 스트림을 만든다 —
   한 번 뽑은 바이트를 `(rand() & 0x0F) + 1`번 반복해 쓴다
3. 앞 4바이트를 뺀 나머지를 그 스트림으로 XOR
4. `4 + (seed & 0x0F)` 자리에서 16바이트 → AES 키

**열쇠 자리가 구현마다 다르다.** 포맷 문서가 이 부분을 정확히 적어 두지 않아서
"섹션 앞머리에서 꺼낸다"는 구현과 "DocInfo 앞머리에서 꺼낸다"는 구현이 공존한다.
그래서 **둘 다 시도하고 평문이 나오는 쪽을 고른다**(`view_text_section`).
판단 기준은 복호·압축해제 결과에서 `PARA_TEXT` 레코드를 훑어 읽을 수 있는 글자가
8자 이상 나오는지다(`looks_like_text`). 열쇠를 못 찾으면 실패가 아니라 `Encrypted`로 남긴다.

**새 의존성은 `aes` 하나**(RustCrypto, MIT/Apache). ECB 블록 복호만 쓴다.
`docs` feature 안에 들어가므로 초경량 빌드에서는 함께 빠진다.

**검증**
- `msvc_rng_matches_c_rand` — 생성기가 C `srand(1); rand()`의 알려진 수열
  (41, 18467, 6334, 26500, 19169, 15724)과 같은지. 이게 틀리면 열쇠를 절대 못 찾는다.
- `distribution_hwp_roundtrip` — **배포용 hwp를 직접 만들어**(키 심기 → 난독화 → deflate →
  AES 암호화 → OLE 컨테이너 작성) 되읽는다. 플래그 판독·ViewText 경로·260바이트 건너뛰기·
  복호·압축해제·레코드 스캔이 이어지는지 확인한다.
- `undecryptable_distribution_reports_encrypted` — 못 푸는 배포용 문서가 `Encrypted`로 남는지.

**실파일 확인 완료** (2026-07-31, 사용자). 왕복 테스트만으로는 열쇠를 꺼내는 자리가 한글의
실제 규칙과 같은지 알 수 없어(같은 규칙으로 넣고 빼므로 자기 일관성만 본다) 실제 배포용 문서로
확인이 필요했고, 통과했다.

다시 확인할 일이 생기면:
```bash
YAMCHA_DOC_SAMPLE=<배포용.hwp> cargo test -p yamcha-core --release real_document -- --ignored --nocapture
```
실패하면 볼 곳은 §9의 4단계 중 어디서 어긋났는지다 —
`distribution_key`에 seed·offset을 찍어 보면 바로 좁혀진다.
