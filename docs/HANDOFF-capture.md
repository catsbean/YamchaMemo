# 7단계 — 담기 (수집 마찰 없애기)

지금 앱은 **꺼내기가 강하고 담기가 약하다.** 검색·회고·백링크·내보내기는 갖춰졌는데,
무언가를 넣으려면 반드시 앱을 열고 분류를 고르고 새 노트를 만들어야 한다.
5단계에서 검색을 강화해 꺼내기가 더 강해진 만큼 이 불균형이 커졌다.

이번 단계의 목표는 하나다 — **본 것을 담는 데 드는 손을 줄인다.**

곁들여 미뤄 둔 작은 것 셋(독서 통계·백업·묶어 보기)을 함께 한다.

---

## 0. 정한 것 (사용자 결정, 2026-07-31)

| 항목 | 결정 |
| --- | --- |
| 빠른 담기 창 | 만든다. **설정에서 켜고 끄고, 기본은 꺼 둔다.** 설정에 `?` 설명 버튼 |
| 담기 목적지 | **설정에서 고른다. 기본은 오늘 일지에 `기록`** |
| URL 붙여넣기 | **제목만** 가져와 `[제목](주소)` |
| 웹 스크랩 | **별도 분류(폴더)를 새로 만든다.** 주소 우클릭 → 스크랩하기 → 팝업에서 고치고 저장/취소 |
| 할 일 이월 | **안 한다** — 대시보드에 미완 할 일이 이미 보인다 |
| 독서 진도(%) | **안 한다** |
| 독서 통계 | 한다. **홈에 한 줄 + 책장에 탭** 둘 다 |
| 백업·복원 | 한다 |
| 묶어 보기 | **묶어 보기 + 정렬**까지 (그리드는 안 함) |

## 1. 참고한 두 프로젝트와 우리의 차이

[obsidian-clipper](https://github.com/obsidianmd/obsidian-clipper) ·
[web-clipper](https://github.com/webclipper/web-clipper) — **둘 다 브라우저 확장이다.**
이 차이가 설계를 가른다.

| | 브라우저 확장 | 우리(데스크톱 앱) |
| --- | --- | --- |
| 무엇을 읽나 | 브라우저가 **이미 그린 화면**(DOM) | 서버가 준 **원본 HTML** |
| JS로 그리는 사이트 | 문제없음 | **본문이 비어 온다** |
| 로그인·유료 기사 | 보고 있는 그대로 담김 | **못 가져온다** |
| 설치 | 브라우저마다 확장 설치 | 앱 하나로 끝 |

**JS로 그리는 사이트가 많다는 점은 이 기능의 성패를 가른다.** 그래서 한 방법에 걸지 않고
**세 갈래를 순서대로** 시도한다. 앞의 것이 싸고 빠르며, 뒤로 갈수록 확실하다.

### 갈래 ① 원본 HTML — `reqwest` + `readability`

주소만 받아 서버가 준 HTML을 긁는다. **싸고 빠르다(0.3초쯤).**
언론사·관공서 공지·블로그 상당수가 서버에서 그려 보내므로 이것으로 끝난다.
본문이 비거나 너무 짧으면(예: 200자 미만) 실패로 보고 ②로 넘어간다.

### 갈래 ② 숨은 창으로 **진짜 렌더링** — 우리도 브라우저 엔진을 품고 있다

이 앱은 Tauri라서 **이미 WebView2(윈도우)·WKWebView(맥)를 안고 다닌다.**
보이지 않는 창을 하나 만들어 주소를 열고, JS가 다 돌기를 기다린 뒤 **완성된 화면(DOM)을 긁는다.**
브라우저 확장이 하는 일과 원리가 같다 — 그것을 우리 앱 안에서 할 뿐이다.

값을 돌려받는 길은 Tauri v2가 공식으로 준다. capability에 `remote` 필드로
원격 페이지에 IPC를 열 수 있다(2026-07-31 문서 확인):

```json
"remote": { "urls": ["https://*"] }
```

**대가와 그 처리**

| 대가 | 어떻게 |
| --- | --- |
| 페이지의 JS가 다 돈다(광고·추적기 포함) | 쿠키·저장소를 **격리한 창**으로 열고 끝나면 버린다 |
| 무한 로딩·자동재생 | **10초 타임아웃** 후 그때까지 그려진 것으로 진행 |
| 느리다(1~3초) | 그래서 ①을 먼저 하고 **실패할 때만** ② |
| 로그인 세션이 없다 | ③으로 넘긴다 |

⚠️ **보안** — `remote.urls`를 열면 그 창에 로드된 아무 페이지나 우리 커맨드를 부를 수 있다.
그래서 **① 숨은 캡처 창에만 주고 ② 권한은 결과를 돌려보내는 이벤트 하나로 좁히고
③ 캡처가 끝나면 창을 닫는다.** 다른 창에는 이 능력을 주지 않는다.

### 갈래 ③ 붙여넣기 — 로그인·유료 기사

②로도 안 되는 것이 남는다(로그인해야 보이는 글, 유료 기사). 이때는 사용자가 브라우저에서
복사해 팝업에 붙여넣는다. **여기서 중요한 사실 하나** — 브라우저에서 복사하면
클립보드에 **서식이 있는 HTML이 함께 실린다**(`arboard`의 `html()`로 읽을 수 있다, 확인함).

그래서 붙여넣기는 맹탕 텍스트가 아니다. 제목·소제목·링크·목록이 살아 있는 채로
같은 변환기(`htmd`)를 태워 마크다운이 된다. **①·②와 품질이 같다.**

---

배울 것은 **구조**다 — 제목·주소·작성자·발행일을 frontmatter로 두고 본문은 마크다운으로,
그리고 저장 전에 사람이 고칠 수 있게 하는 것. 코드를 가져올 것은 없다(TypeScript 확장이다).

**쓸 크레이트**

| 하는 일 | 크레이트 | 라이선스 | 근거 |
| --- | --- | --- | --- |
| 본문 추출 | `readability` 0.3 | MIT | arc90 Readability의 Rust 이식. 최근 다운로드 72만 |
| HTML → 마크다운 | `htmd` 0.5 | Apache-2.0 | turndown.js 계열. 최근 다운로드 140만 |
| 전역 단축키 | `tauri-plugin-global-shortcut` 2 | MIT/Apache | Tauri 공식 |
| zip 쓰기 | `zip` (**이미 있음**) | MIT | 5단계에서 추출용으로 들였다 |

`reqwest`·`scraper` 성격의 HTTP·HTML 처리는 이미 앱에 있다(교보 파서).

## 2. 단계

각 단계 끝에서 검증 게이트를 통과한 뒤 다음으로 간다.
회귀 기준선: **core 149(+ignored 3) + app 14(+ignored 2)**, 감소 금지.

### 7-0-a. 먼저 재 본 것 — Threads (2026-07-31)

계획을 쓰는 중에 실제로 확인했다. 사용자가 준 Threads 공유 주소 2개다.

| 갈래 | 결과 |
| --- | --- |
| ① 원본 HTML (`curl`) | HTTP 200, **257KB를 받았는데 본문은 0자.** `og:title`·`og:description`조차 없다. 60%가 `<script>` |
| ② 렌더링 (실제 브라우저 엔진) | **본문 전부 + 이어지는 답글까지 그대로.** 로그인 없이 |

**갈래 ②가 필요하다는 것이 실측으로 확인됐다.** ①만으로는 이런 사이트가 통째로 빠진다.

여기서 하나 더 알게 된 것 — **렌더링해서 얻은 텍스트에는 군더더기가 섞인다.**
"로그인", "조회 4.6천회", 좋아요·답글 수 같은 숫자가 함께 딸려 온다.
`readability`는 **기사용 휴리스틱**이라 이런 피드형 페이지에서 본문만 골라내지 못할 수 있다.

→ 설계 보완: 렌더링 결과에 `readability`를 태우되, **결과가 빈약하면 렌더링된 텍스트 전체**를
넣고 사람이 팝업에서 다듬게 한다. 스크랩 팝업이 "고칠 수 있게" 되어 있는 것이 여기서 값을 한다.
게다가 소셜 글타래는 **답글까지가 담고 싶은 내용**인 경우가 많아, 전체를 넣는 편이 나을 때가 있다.

### 7-0. 본문 추출 스파이크 — ✅ 완료 (2026-07-31)

`readability` 0.3 + `htmd` 0.5로 한국 사이트 15건 측정. 본문 200자 이상을 성공으로 본다.

**갈래 ① (원본 HTML)**

| 사이트 | 성격 | 본문 글자 | ms | 판정 |
| --- | --- | --- | --- | --- |
| ko.wikipedia.org (마크다운) | 서버 렌더링 | 3,602 | 1,153 | ✅ |
| ko.wikipedia.org (한국어) | 서버 렌더링 | 43,333 | 913 | ✅ |
| github.com (README 2건) | 서버 렌더링 | 8,976 / 3,016 | 899 / 751 | ✅ |
| namu.wiki (2건) | SPA지만 SSR | 309 / 4,489 | 494 / 579 | ✅ |
| velog.io (2건) | SPA지만 SSR | 1,877 / 667 | 338 / 90 | ✅ |
| news.hada.io (2건) | 서버 렌더링 | 268 | 70 / 94 | ✅ |
| news.nate.com | 서버 렌더링 | 79 | 254 | △ |
| brunch.co.kr | — | — | 338 | ✗ 리다이렉트 오류 |
| threads.com | **JS 렌더링** | 7 | 369 | ✗ |
| d2.naver.com | **JS 렌더링(SPA 껍데기 4KB)** | 7 | 120 | ✗ |

**성공 10/14** (내 주소 오류로 404가 난 1건 제외). 소요는 대개 **0.1~1초**.

**갈래 ② (실제 렌더링) — ①이 실패한 것에만 걸어 봤다**

| 사이트 | ① | ② |
| --- | --- | --- |
| threads.com | 본문 7자 | **본문 전부 + 답글까지** ✅ |
| brunch.co.kr | 리다이렉트 오류 | **본문 전부** ✅ |
| news.nate.com | 79자 | 79자 수준 — **페이지 자체가 얇았다**(지표 나열 기사). ①의 잘못이 아니다 |

**이것으로 정해진 것 넷**

1. **갈래 ①을 기본으로 둔다.** 10/14가 0.1~1초에 끝난다. 놀란 것은 **velog·나무위키가 ①로 됐다는 점** —
   SPA처럼 보여도 서버에서 한 번 그려 보내는 사이트가 많다. "SPA면 무조건 ②"는 틀린 짐작이었다.
2. **갈래 ②는 진짜로 필요하다.** Threads·D2처럼 껍데기만 오는 사이트는 ①로 절대 안 된다.
   그리고 ②를 걸면 **된다**(실측).
3. **실패 사유를 갈라 봐야 한다.** ①의 실패가 다 같은 실패가 아니었다 —
   JS 렌더링(threads·d2) · 리다이렉트/쿠키(brunch) · 원래 얇은 문서(nate).
   앞의 둘만 ②로 넘기면 되고, 셋째는 ②로도 안 는다. 그래서 **①의 결과가 짧다고 무조건 ②를 돌리면
   헛일**을 한다 → 200자 미만이면 ②를 시도하되, ②의 결과도 짧으면 그대로 받아들이고 사용자에게 보여 준다.
4. **brunch의 리다이렉트 오류**는 `reqwest`의 리다이렉트 정책 문제로 보인다(쿠키를 요구하는 듯).
   구현할 때 쿠키 저장소를 켜고 다시 확인할 것.

**게이트 통과** — ①만으로 71%, ②를 더하면 이보다 높다. 붙여넣기(③)를 기본으로 승격할 이유가 없다.

측정 도구는 저장소 밖 스파이크 프로젝트에 있다(`webspike`, urls.txt를 받아 result.md를 쓴다).

### 7-1. 빠른 담기 창

- `tauri-plugin-global-shortcut` 추가
- 설정 > 일반에 **"빠른 담기"** 항목
  - 켜기/끄기 (**기본 꺼짐**)
  - 단축키 (기본 `Ctrl+Shift+Space`, 바꿀 수 있게)
  - 담을 곳: **오늘 일지에 기록**(기본) / 수집함 노트 / 스크랩 분류
  - **`?` 버튼** — 눌러 펼치면 설명이 나온다(아래 문안)
- 작은 창: 한 줄 입력 + `Enter` 담고 닫기 + `Esc` 취소.
  담은 뒤 "담았습니다" 한 줄만 보이고 사라진다
- 끄면 단축키를 **해제**한다 (켜 두지 않은 사용자에게 단축키를 빼앗지 않는다)

**`?` 설명 문안**
> 다른 프로그램을 쓰는 중에도 단축키 한 번으로 작은 입력창을 띄워, 지금 떠오른 것이나
> 복사해 둔 것을 앱을 열지 않고 바로 담습니다. 담긴 것은 아래에서 고른 곳에 한 줄로 쌓입니다.
> 꺼 두면 단축키를 쓰지 않으므로 다른 프로그램의 단축키와 부딪히지 않습니다.

- 검증: 앱이 **뒤에 있을 때** 단축키가 먹는지 · 창이 포커스를 가져갔다 되돌려주는지 ·
  끄면 단축키가 풀리는지 · 다른 앱과 충돌 시 안내가 뜨는지 · 일지가 없으면 만들어지는지
- 커밋: `7단계-1 — 빠른 담기 창`

### 7-2. URL 붙여넣기 — ✅ 완료 (2026-08-01)

**언제 끼어드나** — 붙여넣는 클립보드 텍스트를 trim한 결과가 정확히 `http(s)://...`
하나뿐일 때만 가로챈다. 앞뒤에 다른 글자가 있거나 여러 줄이거나 이미 `[제목](url)`
형식이면 기본 붙여넣기로 넘어간다. `Editor.tsx`의 `pasteImage`와 같은 자리, 같은 패턴.

**흐름 — "먼저 넣고, 되면 바꾼다"**
1. 붙여넣는 즉시 URL을 그대로 삽입한다 (타이핑이 네트워크를 기다리지 않는다)
2. 그 구간을 CodeMirror `StateField`로 추적한다 — 문서가 편집돼도 위치가 따라와야 한다
   (문서 변경마다 `RangeSet.map`으로 좌표를 옮긴다)
3. 그 구간 끝에 **위젯 데코레이션**으로 `⏳ 가져오는 중…`을 보여 준다.
   실제 문서 텍스트를 건드리지 않는다 — 지금 저장해도 URL만 있는 정상 마크다운이다.
   (`livePreview.ts`가 이미 쓰는 `Decoration`/`WidgetType`/`ViewPlugin` 그대로 재사용)
4. 비동기로 `fetch_page_title(url)`을 부른다 (타임아웃 5초)
5. 응답이 오면 **그 구간의 지금 텍스트가 여전히 같은 URL인지 확인 후** `[제목](url)`로 바꾼다.
   사용자가 그 사이 지우거나 고쳤으면 — 건드리지 않고 조용히 위젯만 사라진다
6. 실패(오프라인·타임아웃·제목 없음·**의미없는 제목**)해도 건드리지 않는다 — URL만 남는다

**의미없는 제목 판정** — threads.com처럼 SPA 껍데기가 `<title>Threads</title>`만
주는 경우(7-0에서 실측 확인)를 실패로 본다. 제목을 소문자·공백 제거한 값이
**호스트 이름의 첫 라벨과 같으면** 실패로 판정한다(`threads.com` → `threads` == 제목
`Threads`를 소문자화한 것). 순수 함수 `is_meaningless_title(title, host)`로 분리해
단위테스트를 붙인다.

**백엔드**
- 새 커맨드 `fetch_page_title(url: String) -> Result<Option<String>, String>`
- 새 의존성 없음 — `http_client()`·`html_unescape`가 이미 있다. 다만 붙여넣기용이라
  기존 15초 클라이언트 대신 **3~5초짜리 짧은 타임아웃 클라이언트**를 따로 둔다
- `<title>...</title>` 정규식 추출 → `html_unescape`로 엔티티 해제 → 공백/줄바꿈 정리 →
  `is_meaningless_title`로 걸러 `None`이면 실패

**적용 범위** — 이번엔 편집기(CodeMirror)만. 빠른 담기 창(textarea)에는 넣지 않는다.
검증할 곳이 늘고, 담기 창은 한 줄짜리 잡담이용이라 원문 URL이 그대로 남는 게 더 낫다.

**검증**
- 실앱: 위키백과·GitHub·나무위키(7-0에서 이미 ①로 성공 확인) · 오프라인 · 404 ·
  순수 URL이 아닌 글 붙여넣기(건드려지지 않아야 함) · threads.com(그대로 남아야 함) ·
  응답 오는 동안 그 자리를 지우고 다른 곳에 붙여넣기(엉뚱한 곳이 안 바뀌어야 함)
- 단위: `is_meaningless_title` · `<title>` 추출 · 엔티티 해제 · 실패 케이스들


**구현하며 드러난 것 — 실제 위키백과가 403을 준다.** `quick_http_client()`를 UA 없이
만들었더니 위키백과가 403 Forbidden으로 막았다(교보가 UA 없는 요청을 500으로 막던 것과
같은 종류). 처음엔 바이트 경계 버그로 의심하고 되짚었는데, 실제 원인은 UA 누락이었다 —
`cargo test url_paste_live_probe -- --ignored --nocapture`로 실제 네트워크에 대고
확인해서 잡았다. 기존 교보용 `KYOBO_UA`를 `BROWSER_UA`로 승격해 두 클라이언트가
같이 쓰게 했다.

**실앱 검증 결과** (dev + CDP로 실제 붙여넣기 이벤트를 만들어 확인)

| 시나리오 | 결과 |
| --- | --- |
| 위키백과 실제 URL 3종(마크다운·한국어·GitHub) | `[실제 제목](url)`로 정확히 바뀜 |
| threads.com (의미없는 제목) | `<title>Threads</title>`뿐 → 실패 판정, URL 그대로 남음 |
| 없는 페이지(404류) | `fetch_page_title` → `null`, 손대지 않음 |
| 문장 속에 섞인 URL | 가로채지 않고 기본 붙여넣기로 그대로 들어감 |
| 붙여넣은 자리 밖을 편집(그 뒤에 타이핑) | 정상적으로 링크로 바뀜 (편집이 구간 밖이라 안전) |
| 붙여넣은 URL 자체를 편집(끝을 지움) | 그 자리는 더는 원본과 안 같아서 바꾸지 않음 — 원문이 편집된 대로 남음 |

로딩 위젯(`⏳ 가져오는 중…`)이 실제로 뜨고 사라지는 것, 저장한 파일에 순수 마크다운
(`[제목](url)`)만 남고 위젯 흔적이 안 남는 것도 확인했다.

**단위 테스트** — `extract_title`(엔티티·공백 정리) · `host_label` · `is_meaningless_title`
(threads.com 실측 케이스 포함) · `fetch_page_title`가 나쁜 주소에 조용히 `None`을 주는지.

커밋: `7단계-2 — URL 붙여넣기`

### 7-3. 웹 스크랩

**새 분류를 하나 만든다.** "어디서든 본 정보를 마구 모으는" 자리다.

```
분류 id     scrap
폴더        Scraps
필드        url(주소) · site(출처) · author(글쓴이) · published(발행일) · tags
제목 기본값  {날짜} {페이지 제목}
```

- 주소 우클릭 메뉴에 **"스크랩하기"**
- 팝업(수정 가능):
  - 제목 — 기본 `2026-07-31 기사 제목`
  - 주소 — frontmatter `url`로 들어감
  - 본문 — 추출한 마크다운. **여기서 고칠 수 있다**
  - 본문을 못 가져왔으면 안내 + 붙여넣기 칸("브라우저에서 복사해 여기 붙여넣으세요")
- **저장** = 파일로 쓰고 창 닫기 · **취소** = 아무것도 남기지 않는다
- 새 커맨드 `fetch_article(url) -> { title, body_md, site, author, published, via }`
  — `via`는 어느 갈래로 얻었는지(`html`/`render`/`paste`). 화면에 작게 보여 주면
  "왜 이건 본문이 없지"를 사용자가 스스로 안다
- 갈래 ②(숨은 렌더링 창)는 여기서 만든다. 진행 표시는 "페이지를 여는 중…"
- 팝업에 **"브라우저에서 복사해 붙여넣기"** 칸을 늘 둔다 — ②까지 실패했을 때의 길이자,
  ②가 엉뚱한 부분을 잡았을 때 사용자가 직접 고쳐 넣는 길이다

**설계 결정 — 파일은 저장을 눌러야 생긴다.** 먼저 만들고 취소 때 지우면
휴지통·히스토리·감시가 다 얽힌다. 팝업이 닫힐 때까지 메모리에만 둔다.

- 검증: 한국 기사 3종 · JS 렌더링 사이트(실패 안내가 뜨는지) · 취소 후 파일이 없는지 ·
  붙여넣기 경로로도 저장되는지 · 스크랩 노트가 검색·태그·백링크에 정상으로 잡히는지
- 커밋: `7단계-3 — 웹 스크랩`

## 3. 무게 예산

5단계에서 정한 규율을 잇는다. 실행파일 증가는 **≤ +3MB**를 목표로 한다.

| 새로 드는 것 | 예상 |
| --- | --- |
| `readability` + `htmd` | 1~2MB (순수 Rust, 모델·사전 없음) |
| `tauri-plugin-global-shortcut` | 수백 KB |
| `arboard` (클립보드 HTML) | 수백 KB |
| **숨은 렌더링 창** | **0 — 이미 품고 있는 WebView를 쓴다** |
| 차트 라이브러리 | **0 — 들이지 않는다** (CSS 막대) |

갈래 ②가 무게를 하나도 안 쓴다는 것이 이 설계의 값이다. 브라우저 엔진을 새로 들이는 것이
아니라 **앱이 이미 안고 다니는 것을 한 번 더 여는 것**이다.

빠른 담기를 꺼 두면 단축키를 등록하지 않으므로 **런타임 비용도 0**이다.

## 6. 검토했으나 쓰지 않는 것 — browser-rs (2026-07-31)

[browser-rs](https://github.com/maestrojeong/browser-rs-mcp)를 살펴봤다.
**AI 에이전트가 브라우저를 조종하게 해 주는 MCP 서버**다. 설치된 크롬에 CDP로 붙고,
5.5MB에 메모리 6MB로 가볍다. 만듦새는 좋다.

**우리 앱에는 넣지 않는다.** 이유가 셋이다.

1. **성격이 다르다** — MCP 서버는 *AI가* 브라우저를 쓰라고 만든 것이다.
   우리가 만드는 것은 *사람이* 보고 있던 글을 담는 클리퍼다. 단독 실행 바이너리이고
   라이브러리로 공개된 API가 없다.
2. **크롬 설치를 요구한다** — 우리는 이미 WebView2·WKWebView를 품고 다닌다.
   "클리핑하려면 크롬을 까세요"는 앱 하나로 끝난다는 이 프로그램의 성격에서 후퇴다.
3. **무게** — 5.5MB짜리 서버를 함께 배포하고 프로세스를 띄워야 한다. 갈래 ②는 0MB다.

**다만 하나는 진짜 장점이라 적어 둔다.** browser-rs는 **사용자가 늘 쓰는 크롬 프로필
(로그인·쿠키)을 그대로** 쓴다. 갈래 ②의 유일한 약점이 "로그인 세션이 없다"인데
그것을 정면으로 푼다. 그리고 봇 탐지에도 강하다 — 분장한 브라우저가 아니라 진짜니까.

그래서 판정은 **"지금은 아니고, 조건이 생기면 그때"**다.
