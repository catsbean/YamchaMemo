# 8단계 — 1.0으로 가기

7단계까지로 **기능은 충분하다.** 1.0이 가르는 것은 기능이 아니라 "모르는 사람에게 줘도 되는가"다 —
업데이트가 끝까지 되는가, 문제가 났을 때 원인을 볼 수 있는가, vault가 커져도 버티는가,
다음 판에서도 이 판의 노트가 그대로 열리는가, 처음 쓰는 사람이 10분 안에 막히지 않는가.

이 문서는 그 다섯을 순서대로 한다. 작업 지시서이자 결과 기록이다(7단계의 `HANDOFF-capture.md`와 같은 결).

## 0. 정한 것 (사용자 결정, 2026-10-01)

| 항목 | 결정 |
| --- | --- |
| 범위 | 아래 8-1 ~ 8-5. 끝나면 1.0.0 |
| **코드 서명** | **하지 않는다** — 인증서 값(Windows 인증서·Apple Developer 연 99달러)이 이 프로젝트에 비해 크다. 대신 `설치방법.md`의 경고 넘기기 안내(Windows "추가 정보 → 실행", Mac `mac-unlock`)를 첫 화면처럼 다듬는다(8-5) |
| 범위 밖 | 모바일, AI 기능, 형태소 분석기, 외부 폴더 색인 — 이미 내린 결정 그대로(`ROADMAP.md`) |

## 1. 순서와 그 이유

```
8-1  업데이트 끝까지 확인 (0.7.1)       ← 1.0 이전 판을 쓰는 사람이 1.0을 "받을" 수 있어야 한다
8-2  로그·진단 정보·오류 문구           ← 8-3·8-5에서 막히는 곳을 볼 눈이 먼저 있어야 한다
8-3  1만 편 규모 실측                   ← 재고 나서 고친다 (측정 없이 가상화부터 넣지 않는다)
8-4  vault 형식 고정과 이전 장치         ← 1.0의 약속. 8-3에서 형식을 건드릴 일이 생길 수 있어 그 뒤에
8-5  처음 쓰는 사람의 10분              ← 마지막에 — 앞의 것이 다 들어간 화면으로 시험한다
→    1.0.0
```

**8-1이 맨 앞인 까닭**: 자동 업데이트는 0.7.0에 들어갔지만 내려받기·서명 확인·설치를 끝까지 본 적이
없다. 이게 안 되면 0.7.x를 쓰는 사람은 1.0을 손으로 다시 깔아야 한다 — 지금 고칠수록 싸다.

**8-2가 8-3 앞인 까닭**: 1만 편 실측에서 느리거나 실패하는 자리를 찾을 때 로그가 있어야 하고,
8-5의 새 사용자 시험에서 "안 돼요"를 들었을 때 진단 정보를 받아 볼 수 있어야 한다.

## 2. 단계

각 단계는 **검증 게이트를 통과한 뒤 커밋**하고 다음으로 간다. 게이트 공통:
`cargo clippy --workspace --all-targets -- -D warnings` · `cargo test --workspace` ·
`cargo test -p yamcha-core --no-default-features` · `pnpm test` · `npx tsc --noEmit` ·
커맨드를 바꿨으면 바인딩 재생성(`HANDOFF.md` §2.3) · 실제 앱 확인은 testvault로 띄운 개발 빌드에서
(`get_vault_path`로 루트부터 확인). 의존성을 바꾸기 전엔 E: 여유부터 본다(`HANDOFF.md` §7-48).

### 8-1. 업데이트 끝까지 확인 — 0.7.1

**진행 (2026-10-02)**: 코드 쪽은 끝 — `CHANGELOG.md`(0.7.0·0.7.1 절), `scripts/changelog.mjs`(절 뽑기,
시험 5개 — `0.7.1`이 `0.7.10`을 잡지 않는다 등), release.yml이 그 절을 `releaseBody`로 넘긴다(tauri-action이
그 값을 `latest.json`의 `notes`로 쓰는 것을 원본에서 확인), release.bat은 절이 없으면 태그 전에 멈춘다
(cmd로 있을 때·없을 때 확인), 업데이트 창은 설명을 목록으로 보이고 다섯 줄 넘으면 접는다.
**남은 것**: 0.7.0 설치본에서 0.7.1로 실제 업데이트.

**목표**: 0.7.0에서 [새 버전 확인] → [내려받아 설치하고 다시 켜기]로 0.7.1이 깔리는 것을 실제로 본다.
곁들여, 지금은 비어 있는 업데이트 창의 설명(`latest.json`의 `notes`)을 채운다.

- **바뀐 내용 적기**: 루트에 `CHANGELOG.md`(판마다 `## 0.7.1` 절). 릴리스 워크플로가 태그의 절을 뽑아
  tauri-action `releaseBody`로 넘긴다 — 릴리스 설명과 `latest.json`의 `notes`가 같이 채워진다.
  (설명은 **빌드할 때** 정해진다 — Publish 전에 고쳐도 `latest.json`엔 안 들어간다. 0.7.0에서 확인)
- `scripts/release.bat`: 그 판의 절이 `CHANGELOG.md`에 없으면 멈춘다(빈 설명으로 내보내지 않게).
- 업데이트 창: 설명이 길면 접어 보이고, 마크다운 목록(`- `)은 줄로 보인다.
- **사용자가 할 일**: 0.7.0을 손으로 설치해 둔다 → 0.7.1 Publish 뒤 설정 > 버전에서 업데이트.
- 게이트: 공통 + 0.7.1의 `latest.json`을 받아 서명을 앱 공개 키로 검증(`verify-sig.mjs` 방식) +
  **실제 설치본에서 업데이트가 끝까지 됨**(설치 뒤 버전 0.7.1, 노트·설정이 그대로).
  Mac은 가능하면 같은 확인, 안 되면 결과에 "Windows만 확인"이라고 적는다.
- 실패하면: 그 자리의 로그가 없으므로 사용자에게 재현을 부탁하고 계측을 심는다
  (메모리 "재현 안 되면 사용자에게 재현 요청").
- 커밋: `8단계-1 — 바뀐 내용을 업데이트 창과 릴리스에 싣는다` → `release: v0.7.1`(release.bat)
- 문서: 이 문서에 결과, `RELEASE.md`에 CHANGELOG 절차.

### 8-2. 로그·진단 정보·오류 문구

**목표**: 사용자가 "안 돼요"라고 할 때 원인을 볼 수 있게 한다. 지금은 오류가 `eprintln!`(7곳)과
화면 토스트로만 나가고 어디에도 남지 않는다.

- **로그 파일** — 새 의존성 없이 앱 크레이트에 작은 기록기(`log.rs`):
  - 자리: 앱 데이터 폴더의 `logs/yamcha-YYYY-MM-DD.log`, **7일·파일당 5MB**까지(넘으면 오래된 것부터 지움)
  - 남기는 것: 앱 시작(버전·OS)·vault 열기(편수·걸린 시간)·커맨드 실패·색인 따라잡기 실패·
    감시 오류·업데이트 결과·**패닉**(`std::panic::set_hook`)
  - 화면 오류도 남긴다: 스토어 `guard()`가 잡은 오류와 `ErrorBoundary`가 잡은 렌더 오류를
    `log_client_error` 커맨드로
  - **노트 내용은 남기지 않는다.** 경로는 남기되 사용자 폴더 앞부분은 `~`로 줄인다
  - `eprintln!` 7곳을 이 기록기로 바꾼다
- **진단 정보 복사** — 설정 > 도움말에 [진단 정보 복사]: 앱 버전·OS·vault 규모(노트·첨부 수와 크기,
  분류별 편수)·켜 둔 기능(첨부 검색·빠른 담기 등)·최근 로그 200줄. 내용·제목은 넣지 않는다.
  복사하기 전에 무엇이 들어가는지 화면에 보인다. [로그 폴더 열기]도 곁에.
- **오류 문구** — 사용자가 보는 오류를 한 번 훑는다:
  - `CoreError::Io`의 `IO 오류: {원문}`을 흔한 종류별 한국어 문장으로(없음·권한·사용 중·디스크 가득·
    클라우드 미다운로드). 원문은 로그에만
  - 프론트에서 `String(e)`를 그대로 띄우는 자리를 찾아(grep) 같은 원칙으로
- 시험: 기록기의 날짜·크기 넘김, 오래된 파일 지우기, 경로 줄이기, 패닉 기록. `Io` 문구 변환.
- 게이트: 공통 + 실제 앱에서 일부러 실패를 만들어(읽기 전용 파일 저장 등) 로그에 남고 화면 문구가
  한국어 완결문인지 + 진단 정보에 노트 내용이 없는지 눈으로 확인.
- 커밋: `8단계-2 — 로그 파일과 진단 정보, 사용자가 보는 오류 문구 정리`
- 문서: `HANDOFF.md` §1 지도(`log.rs`)·§7 함정, `README.md` "문제가 생기면" 절(진단 정보 보내는 법).

### 8-3. 1만 편 규모 실측

**목표**: 노트 1만 편 + 첨부 2GB에서 무엇이 느린지 **재고**, 문턱을 넘는 것만 고친다.
(지금까지는 2,000편으로만 쟀다. 목록 가상화는 "범위 밖"으로 미뤄 왔다 — 재 보고 정한다.)

- **만들기**: `--ignored` 시험으로 합성 vault 생성기(분류 고르게·링크·태그·할 일·책 표지·첨부 pdf/hwp
  섞어서). 자리는 **저장소 밖**(스크래치나 `%TEMP%`) — 2GB를 저장소에 만들지 않는다. E: 여유 먼저 확인.
- **잴 것**(모두 **release 빌드**, 디버그 수치는 15배 틀린다 — 메모리 "성능은 재고 나서"):

  | 항목 | 문턱 |
  | --- | --- |
  | 첫 실행 전체 색인 | 진행이 보이고 끝나면 됨(시간 기록) |
  | 다음 실행(바뀐 것 없음) | 2초 |
  | 목록 화면 첫 그리기(1만 줄) | 200ms |
  | 메뉴 옮기기·스크롤 프레임 | 100ms / 16ms |
  | 검색 p95 | 100ms |
  | 저장 왕복(자동저장 1회) | 100ms |
  | 모두가 가리키는 노트 제목 바꾸기 | 진행이 보이고 앱이 안 멈춤 |
  | 할 일 탭·회고(한 달)·통계 | 200ms |
  | 백업(2GB) | 진행이 보이고 앱이 안 멈춤, 걸린 시간·크기 기록 |
  | 메모리(작업 관리자) | 기록만 |

- 프론트 수치는 실제 앱에 CDP로 붙어 잰다(이벤트 루프 지연 + 잠금과 무관한 커맨드 왕복 —
  메모리 "한글 IME 실제 검증법"의 계측법).
- **문턱을 넘는 것만** 고친다. 목록이 넘으면 그때 가상화(라이브러리를 들일지는 무게를 재고 결정).
- 게이트: 공통 + 고친 항목의 전/후 수치 + 2,000편 수치가 나빠지지 않았는지.
- 커밋: `8단계-3 — 1만 편 실측` (측정 결과만) + 고친 것마다 따로
- 문서: 이 문서에 수치 표(전/후), `HANDOFF.md` §2.2 측정 명령.

### 8-4. vault 형식 고정과 이전 장치

**목표**: "이 판에서 쓴 노트는 다음 판에서도 그대로 열린다"를 약속으로 만든다. 지금은 형식이 바뀔 때
그때그때 맞춰 왔다(`ensure_aliases_field`, `migrate_readings`) — 판 표시도 차례도 없다.

- **형식 문서** `docs/VAULT-FORMAT.md`: 폴더 규칙(분류 폴더·데일리 연/월·`_attachments`), 파일명 규칙,
  frontmatter 칸(분류별, 필수·선택·종류), 책 본문 두 절, 콜아웃·할 일 문법, `_types.json`·`_callouts.json`,
  `.yamcha/`의 각 자리, 앱이 만드는 `_index.md`. **다른 편집기(옵시디언)로 고쳐도 되는 것과 안 되는 것.**
- **판 표시**: `.yamcha/format.json` `{"version": 1}`. 백업에 넣는다(`backup.rs`의 넣는 규칙에 추가).
- **이전 장치**: `migrations.rs` — 판 번호 차례대로 도는 이전 목록. 기존의 `migrate_readings`·
  `ensure_aliases_field`를 0→1 이전으로 옮긴다. `Vault::open`이 판을 보고:
  - 표시가 없거나 낮으면 → 이전하고 판을 올린다(이전 전에 바뀔 파일은 휴지통이 아니라 `.yamcha/migrate-backup/`에 사본)
  - **더 높으면 → 열지 않는다**: "이 vault는 더 새 판(0.x)에서 만들었습니다. 앱을 업데이트하세요." +
    [새 버전 확인]. 옛 앱이 새 형식을 망가뜨리지 않게
- 시험: 표시 없는 옛 vault → 1로 이전(기존 이전 시험이 그대로 통과), 판 2 vault → 열기 거부,
  이전이 두 번 돌아도 같은 결과, 백업에 `format.json`이 들어감.
- 게이트: 공통 + 실제 앱에서 testvault 사본으로 열기(이전 전/후 파일 비교) + 판을 높인 사본에서 거부 문구.
- 커밋: `8단계-4 — vault 형식 문서와 판 표시, 이전 장치`
- 문서: `VAULT-FORMAT.md`(새), `README.md`에서 연결, `HANDOFF.md` §7(형식을 바꿀 땐 이전을 같이 쓴다).

### 8-5. 처음 쓰는 사람의 10분

**목표**: 설치 → 저장 위치 고르기 → 첫 노트 → 책 한 권 → 검색까지, 처음 보는 사람이 막히지 않는다.

- **설치 경고 안내**(코드 서명을 안 하므로 가장 먼저 만나는 벽): 릴리스 설명 첫머리와 `README.md` 설치
  절에 `설치방법.md`의 경고 넘기기를 그림과 함께 바로 보이게. 릴리스 설명은 8-1의 `CHANGELOG.md`
  절 위에 고정 머리말로 붙인다.
- **내가 먼저 돌려 보기**: 새 설정·빈 vault로 개발 빌드를 띄워(설정 파일은 백업해 두고 끝나면 되돌린다 —
  사용자 설정을 건드리므로 그 자리에서 다시 묻는다) 첫 화면부터 순서대로 밟고, 막히는 곳·빈 화면·
  설명 없는 버튼을 목록으로.
- **사람 시험**: `docs/USER-TEST.md` — 처음 쓰는 사람 한 명에게 줄 과제 5개와 관찰 기록 칸
  (설명 없이 과제만 준다. 어디서 멈췄는지·무엇을 찾았는지 적는다). **사용자가 사람을 구해 진행한다.**
- 고칠 것은 두 시험의 목록에서 고른다(빈 화면 안내, 첫 실행 도움말, 용어 등). 새 기능은 만들지 않는다.
- 게이트: 공통 + 고친 뒤 새 설정으로 한 번 더 처음부터.
- 커밋: `8단계-5 — 처음 쓰는 사람의 10분` (고친 것마다 따로)
- 문서: `USER-TEST.md`(새, 결과 포함), `설치방법.md`·`README.md`.
